## 4. 这轮踩到/修掉的坑

1. **假服务不关连接 → 客户端挂 120s**：Python `BaseHTTPRequestHandler` 默认 HTTP/1.1 keep-alive，`data: [DONE]` 后不 EOF，`Invoke-WebRequest` 与 OkHttp 都会一直等。修法：所有响应加 `Connection: close` + `self.close_connection = True`。
   顺带修掉一个**假故障**：429 用例一度耗时 16.4s（因为 429 的 JSON 响应也没关连接），改成 close 后降到 **0.354s**。
2. **USB 掉线，设备序列号从 `<设备序列号>` 变成 `192.168.1.3:5555`**：`adb reverse` 是绑在 transport 上的，USB 一断映射全丢，仪器测试于是全部"连接被拒"。已确认 `ro.serialno` 仍是 `<设备序列号>`（同一台机）。
   处置：环境脚本新增 `Get-AskFirstSerial`（自动取第一个在线设备），以后所有脚本/文档不再硬编码序列号。
3. **给 `adb reverse` 的教训**：跑仪器测试前先 `adb devices` 看序列号，并重新 `reverse`；无线 adb 也能跑，但要在同一 Wi-Fi。

## 5. 与施工清单的偏差

- `HttpFactory` 的 `callTimeout=0`（不设总时长）：流式的总预算交给上层（引擎 60s / 用户取消）。S4 的引擎会加 `withTimeout`，这里不多设一层。
- 接口 `LlmProvider` 现在有 3 个方法（`config/ping/stream`）。S3 前只声明了 2 个，属于"只加不改"。

## 6. 遗留

- 真实服务（DeepSeek/Kimi）的成功路径还没跑（等 Key）。**当前证据已覆盖**：分帧、语义、增量、收尾、429、拒连、乱数据——真 Key 只影响"服务端行为差异"，不影响通道本身的正确性。
- 首字 <2s 是**对着本机假服务**量的（不含真实网络 RTT）。真机+M1-03 验收时要在真服务上复测一次并记录。

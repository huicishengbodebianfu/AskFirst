## 一、最重要的一条：产品化会杀死这个方法

Matt Pocock 有一份文档专门记录他**拒绝**的两个需求，读完我出了一身冷汗——
两条都是 AskFirst 正在做的事：

**① 拒绝硬性题数上限**（`.out-of-scope/question-limits.md`）
原文理由：问题多是**提示词质量问题，不是数量问题**，"fix belongs in the skill
prompt, not in a counter"。硬上限要么砍掉难题上的必要探索，要么在易题上显得武断。
> 直接否定我方案里的「每轮 2~4 题」和 `nudge`（"再聊 2 个问题就够了"）。
> **改：题数不写进引擎逻辑，只作为提示词里的软建议。**

**② 拒绝用结构化选择器 UI 提问**（`.out-of-scope/native-question-tool.md`）
原文：「结构化 picker 会把模型推向**预置答案的多选题**，而这正是 grilling 的反面——
它要的是你用自己的话回答的开放问题，一次一个决策树分支。我试过 AskUserQuestion，
不想要它进这些技能。」有 5 个 issue 请求加这个，全部拒绝。
> 这条对你是**结构性风险**：App 天生有选项 UI，一用就退化成问卷调查。
> 而我们这整场对话就是靠选项 UI 推进的——它让我每轮都只点了第一个字。
> 你自己刚刚演示了这个产品最坏的失败模式。
>
> **对策（必须写进引擎硬约束）**：
> - 默认输出 = **一个开放问题 + AI 的推荐答案**，用户直接打字
> - 选项只在「答案真的对应不同取舍方向」时给，且**强制带「我自己写」**
> - 提示词里明写：开放性问题（描述、痛点、想法）**禁止做成选择题**
>   （这条 ai-prd-generator 也独立写了一遍）

## 二、可以整体搬过来的三件成品

### 2.1 状态机（idea-harness STATE-MACHINE.md）—— 替换我方案里的「覆盖判定」

我现在的设计是平铺的：AI 报告哪些题覆盖完了。太弱。别人的四状态：

| 状态 | 条件 | 输出 |
|------|------|------|
| `gathering` | 还有门槛未回答 | 继续问下一个最重要缺口 |
| `needs-precision` | **都答了，但答得不准** | 追问指向精确度缺口，不开新维度 |
| `blocked` | 冲突 / 说「都要」/ 说「你决定」未确认 / 隐含危险假设 | 只处理阻断 |
| `ready` | 门槛齐 + 精确度全过 + 无阻断 | 出简报 |

关键在 `needs-precision` 这一档——它拦住的正是「表面完整但没法交给下游」的需求。
我的方案里完全没有这一层。**「还没聊完」和「聊完了但没用」是两个不同的失败。**

还有两个细节非常值钱：
- **决策树优先级**：门槛不按 1-7 线性问。痛点没清楚后面全无法判断；
  「主动作」依赖「用户/场景」的答案；「范围边界」在主功能定了才自然产生。
- **回退规则**：只有 `ready` 能回退到 `gathering`（用户改已确认内容）；
  `needs-precision` **不许跳过**直接到 ready。

### 2.2 精确度四项检查（PRECISION-GATE.md）—— 这才是「出单前」该做的事

七门槛答完后逐项跑，任一不过就不是 ready：

1. **目标一致性**：同一个词在不同回答里指的是同一件事吗？
   （例子："记录学习内容" vs "记录学习进度"——"内容"和"进度"是一回事吗？）
2. **隐藏默认值**：回答里暗含了未经确认的假设吗？
   （"保存"暗含数据库？"同步"暗含云端？"分享给朋友"暗含链接生成？）
3. **场景走查**：能从头到尾走完一次具体使用，不撞到未决定的分叉吗？
   （打开→选分类→填金额→记一笔→列表看到→关闭→重开→列表还在。
   "重开还在"没确认 → 就追问那一步。）
4. **矛盾扫描**：已确认的答案两两放一起有没有冲突？
   （"不需要登录"但"每个人看自己的内容" → 矛盾，转 `blocked`。）

第 3 项「场景走查」是我最没想到、也最该进你 App 的——
**它是一个可以离线跑的检查，不需要模型觉得"差不多"了才做。**

### 2.3 六种问法（SKILL.md）—— 比我附录里那 27 道题有用得多

| 问法 | 何时用 | 原话示例 |
|------|--------|---------|
| 具象化 | 用户说了抽象词 | "上一次你觉得管理起来很烦的那个**瞬间**，具体发生了什么？" |
| 反面定义 | 正面需求太宽泛 | "做出来你用了一次就不想用了，最可能的原因是什么？" |
| 假设暴露 | 话里藏着未检验前提 | "你说'同步到手机'——是真的会在手机上操作，还是**只怕电脑上丢**？" |
| 取舍逼问 | 列了多个目标 | "做 A 两天能用，A+B 两周。还都要吗？" |
| 后果推演 | 给了答案没想过下一步 | "假设你存了所有记录，三个月后怎么找到要的那条？" |
| 对比锚定 | 模糊到无法直接追问 | "这跟你现在用备忘录记，最大区别在哪？" |

**提问纪律**（同一文件，逐条都是血泪）：
- 用户回答仍然抽象 → **不换话题，换问法再挖同一个点**
- 说"都要" → 先构造代价场景，再让他选
- 说"你决定" → 给推荐 + **用他自己的场景解释** + 等确认
- 答案冲突 → **把两句原话并排引出来**，只问"哪个是你真正要的"
- 不问实现细节，除非它直接影响用户体验且用户能理解
- **不问用户不可能回答的问题**
- 推荐理由必须引用用户说过的话

### 2.4 歧义词追问表 —— 直接可做 App 的内置知识

"保存 / 通知 / 管理 / 记录 / 分享 / 同步 / 简单" 每个词都备好追问。
例："简单"可能是功能少 / 步骤少 / 界面干净 → "你指的是用起来步骤少，还是功能少？"

还有 **镜像用户用词**：用户说"记一下"就用"记"，不许改成"录入"；
**内部状态绝不暴露给用户**（"门槛""精确度缺口""状态机"这些词不能出现在界面上）。

## 三、grill-with-docs 的教训：你的差异化正在它的已知缺陷里

这个技能是**唯一 stateful 的**同类——它把结论实时写成文件（GLOSSARY.md / ADR），
而不是结束时批量给。判断它工作正常的标准很有意思：

> `GLOSSARY.md` 是在会话**过程中逐条变化**的，而不是最后一次性冒出来。

→ **改你方案：确认单不是一次性生成的产物，而是一张随着回答实时生长的活表。**
   每答完一题，对应栏位当场填上并划掉那一道题。这样你随时知道"还差哪几栏"，
   喊停的时机也就有了依据。这个 UI 改动不大，但产品性质变了。

而它**最严重的公开投诉**，正是你已定的 M4/M5 要解决的：

> 「我其余的决定去哪了？——只留在对话里。这是对该技能最严肃的未决投诉。
> 词汇表不是 spec，多数答案换不来一份 ADR，**没有任何记录把每个已解决的答案
> 连到 spec、ticket 和测试**。后续步骤会把精确的答案（顺序保证、反向要求、
> 数值默认）**软化成更弱的散文**，结果看起来完整，却把你真正定的东西弄丢了。」

这条给你的「全段可溯源」提供了最强理由，并且给出**具体的失败签名**：
不是幻觉，是**软化**。所以溯源之外还要加一条检查：
> **硬答案保护**：数字、日期、"必须先 X 再 Y"、否定式要求（"不要 X"）
> 在方案.md 里必须原样保留，不许被改写成散文。这几类是文档化过程中最先丢失的东西。

to-spec 的 "It's working if" 清单，可直接当**你方案.md 的验收标准**：
- 它开始写，**而不是又问你一轮新问题**
- 用的是**你项目里的名词**，不是通用 PM 模板话术
- **你记得里面每一个决定，它没有为了填满某一节而发明任何东西**
- **out-of-scope 列的是真东西。你拒绝过的那些，通常是全页最有用的几行**
- 还有一句判断准则：**「如果文档让你惊讶，是访谈太浅，不是文档太长」**

一个架构警告：`grill-with-docs` 最常被报告的问题是**部分加载**——
它的 SKILL.md 只有一行委托，依赖没全加载时你会得到"一次把所有题问完且没有推荐答案"。
> **启示：引擎 + 模板 + 出单规则必须在同一个上下文里给模型，不要分层委托。**

## 四、ai-prd-generator：一轮怎么组织的工程细节

- 每轮上限 4 题，**最难/最开放的那题放在一轮的最后**（前面暖场）
- 每轮开头用**一行复述并确认**上一轮的答案
- **预填的答案也必须展示给用户确认，绝不静默假设**
- 不跳过任何没有证据支撑的问题；但——
  > **"一两个有实质的回答，胜过十六个被逼出来的回答。"**
  > 想法还太薄就**停下来直说**，别硬凑轮数。
- **Phase 0 预填**：有现成代码就先挖代码（README 挖出名字/描述/问题，
  package.json 挖技术栈，schema 挖功能，TODO 挖 out-of-scope 候选），
  然后**只问剩下的缺口**，一轮问完。
  → **AskFirst 的等价物你已经有了，就是跨场景引用**：旧确认单能答的先填上，
     让用户确认，而不是重新问一遍。这给 M4 找到了真正的用途（不只是搜索框）。
- **条件轮**：只在触发命中时才问（提到支付才问商业模式），
  且**对跳过的问题只字不提**，不解释"我跳过了 17-20 题"
- 触发命中但答案是"不知道" → **记进 Open Questions，不继续推**
  （"允许存在未知，但不允许缺一节"）→ 完美对应你第 5 栏

# M5 施工清单：方案.md 生成器（三套骨架 / 段落溯源 / SAF 落盘）

> 目标（README 里程碑表 + 方案 §3.5）：确认单之后，把这场问答压成**能直接发给同事看**的
> Markdown 文档：按场景出不同骨架、每段带出处（脚注）、预览可逐段删、可重新生成、
> 能落到手机上一个你自己找得到的文件夹里。
>
> 一句话边界：**扩写只许换说法，不许加事实。**「待决问题」一节不许被漂亮话消化掉。

---

## 1. 范围与不做

做：

- `plan` 表（库 v2 → v3 显式迁移）：一次会话一份方案，段落存 JSON。
- 按场景的三套骨架（技术方案 / 立项 / 复盘）+ 自建场景的通用骨架，
  骨架来自 `scene.planSkeleton`（**M1 起就入库了，v1 已有该列，M5 不动 scene 表**）。
- `PlanBuilder`：一次调用生成整份（JSON 契约），流式进度；断了可「接着写剩下的」
  （第二次调用只补缺的章节）。
- 校验器（纯函数）：章节齐全度、`待决问题` 必须在、漂亮话黑名单、**硬答案保护**
  （文档里的数字/日期必须在原话里出现过）、内部术语黑名单。
- 方案页：预览（章节卡片）/ 每段「这段从哪来」（引原话）/ 逐段删 / 重新生成 /
  接着写剩下的 / 导出（SAF 目录 + 系统分享）。
- 入口：确认单页底部「生成方案.md」；历史详情页（有单子才出现）。

不做（留给后续）：

- 方案的多版本历史（重新生成覆盖同一行）：**确认单才是真相来源**，方案是它的渲染；
  留五个版本只会让人分不清哪份是准的。
- 导 .docx / .pdf；模板皮肤；章节自由增删（只允许按骨架 + 逐段删）。真需要改内容就回去改确认单再重生成。
- 反向溯源（这段被哪份文档引过）。
- 「否定式不软化」的机械检查（要/不要 的改写判断噪声太大，只做提示词约束 + 人工预览）。

## 3. 关键决策

1. **一次会话一份方案**（不建版本历史，§1）。重新生成 = 整份覆盖；逐段删 = 少一段，
   再点重新生成会长回来（这一点在页面上写清楚）。
2. **骨架来自场景，不是代码里写死**：`scene.planSkeleton` 已在库里（M1 留的列），
   `duplicateScene` / 场景 JSON 导入导出都已带着它走。M5 不新增编辑入口——
   自建场景想换骨架就编辑场景 JSON 里的 `planSkeleton`（M3 那条路已经通）。
3. **通用骨架**（自建场景没有骨架时）：概述 / 结论 / 依据 / 行动项 / 待决问题。
4. **「待决问题」是硬门**：骨架里没有含「待决」的章节就自动补一节（复盘骨架的
   「待验证」保留，后面再接一节「待决问题」）。校验器发现这一节缺失/为空/被写成
   「后续持续优化」——**blocking**，页面上直接说「第四节那种漂亮话我不认」。
5. **段落溯源 = message_id，且必须真实存在**：模型只许从上下文给出的候选 id 里挑；
   解析时把不认识的 id 丢掉；丢完一个都不剩的段落**整段删掉**（D4：无出处不产出）。
   UI 里「这段从哪来」把原话按角色列出来；落盘的 .md 里变成脚注 `[^3]` + 文末出处清单。
6. **硬答案保护（改动 #7 的落点）**：文档正文里出现的数字/日期/百分比，
   必须在「这场问答 + 五栏条目」里出现过；否则给 warning 列出漏网的词。
   —— 这一条是防"漂亮话自带一个没发生过的 3 个月排期"。
7. **续写不复用半截 JSON**：`resumeFrom` 把已生成章节的标题交给模型，要求只补缺的。
   比流式半截解析可靠，且用户看得懂「还差 3 节」。
8. **落盘走 SAF 目录授权**（`ACTION_OPEN_DOCUMENT_TREE` + `takePersistableUriPermission`），
   写完给「已存到：<文件夹名>/2026-11-24-缓存改造方案.md」。不写 App 私有目录
   （手机上等于找不到），同时保留系统分享面板（沿用 M2 的 ACTION_SEND 套路）。
   **坑（真机上撞过一次）**：`DocumentsContract.createDocument` 的父目录参数必须是
   `buildDocumentUriUsingTree(treeUri, getTreeDocumentId(treeUri))`；直接传 tree uri，
   AOSP 的 `ExternalStorageProvider` 会抛 `Invalid URI`（见 docs/25 §4）。
9. **温度 0.2 / 3000 tokens / 120s**：比出单更不许发挥；token 比提问流大，但一次就完。
10. **界面零内部词**：说「方案文档」「这段从哪来」「接着写剩下的」，
    不出现 plan/sources/citation/skeleton/JSON。

## 4. 施工顺序

- S1 域层纯函数（骨架/解析/校验/Markdown）+ 单测（先测后写）
- S2 数据层（entity/dao/v3 迁移/repo）
- S3 提示词 + `PlanBuilder` + `PromptBuilder.planMessages` + 门面
- S4 UI（PlanScreen/VM、入口、导航、SAF 导出）
- S5 单测全绿 + 构建门（debug + release）
- S6 真机验收（M5-01~M5-14）+ 假引擎抓请求体（顺手坐实 M4-07）+ 收口文档

## 7. 风险

| 风险 | 处理 |
|---|---|
| 模型把「待决问题」写成漂亮话（方案 §六 最大风险） | 校验器 blocking + 页面明说；提示词里点名禁止 |
| 扩写时编数字/日期 | 硬答案保护（warning 列出漏网词）+ 提示词只给候选事实 |
| 段落出处被模型编造 | 解析时按白名单过滤，段落无合法出处即丢弃 |
| 长文一次出不完（3000 tokens 上限） | 「接着写剩下的」二次补章；页面上标「还差 N 节」 |
| SAF 授权被系统回收 | 每次导出前检查 `persistedUriPermissions`，没了就重新选目录 |
| 方案与确认单不一致（用户改完单子没重生成） | 页面顶部提示「单子改过之后，方案还是旧的」——用 sheet.updatedAt vs plan.createdAt 判断 |

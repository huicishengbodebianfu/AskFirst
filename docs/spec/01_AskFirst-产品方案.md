# AskFirst（暂定代号）产品方案

> 一句话：**一个会反过来问你的 App。** 你带着一个模糊的事开工前先打开它，
> 它按场景一轮一轮追问你，你说「够了」，它把聊天压缩成一份能直接开工的思路确认单。

替代的原始动作：每次做事前新开一个 agent 会话，让它提问帮我理思路。

## 二、核心用户流程

```
打开 App
  → 选场景（技术方案 / 立项 / 复盘 / 我的场景…）
  → 一句话说清要做的事（自由输入，20 字也行）
  → 【循环】AI 问 2~4 个问题 → 我回答 → AI 追问
       每轮底部两个按钮：〔继续答〕〔够了，出确认单〕
  → 出单：五栏卡片，每栏可直接点进去改
  → 三个出口：〔复制成提示词〕〔保存到历史〕〔导出 Markdown〕
  → 〔生成方案.md〕→ 按场景骨架扩写 → 逐段核对溯源 → 落盘/分享
  → 〔调研验证〕→ 检索 GitHub 同类 → 对照方案出「验证报告」→ 结论回写第 2/5 栏
```

注意流程里的这个顺序：**问 → 出单 → 生成方案 → 调研验证**，调研在最后。
这是决策 13 的核心：AI 不许因为「查到过别人怎么做」而少问你问题。
你的答案必须在证据之前完整落地。

中途退出：**自动存草稿**，回 App 首页顶部显示「上次未完成的思路」，点进去接着问。
这条必须做，手机上被打断是常态。

## 三、模块设计

### 3.1 提问引擎（最难，也是这个产品的全部价值）

不能退化成「把模板问题一条条念完」。三条硬规则：

1. **覆盖判定**：每个模板问题有 id，AI 每轮输出「已被我的回答覆盖的问题 id 列表」。
   已覆盖的不再问，跳过去问没覆盖的。
2. **追问优先于跳题**：我一句话只答了某个问题的三分之一时，先就这一条追问，
   不要礼貌性地说「好的」然后跳下一题。这是体验分水岭。
3. **不编造**：出单时只允许写我明确说过的内容。信息缺失就写进第 5 栏「还没想清楚的问题」，
   不许用漂亮话填空。

**每轮的模型输入结构**

```
system: 提问引擎人设 + 输出 JSON schema
scene : 当前场景的问题清单（id + 问题 + 为什么问）
intent: 用户最初那句话
covered: 已覆盖问题 id 列表
thread : 本次会话的完整问答
history: （可选）跨场景引用的旧确认单摘要
```

**每轮的模型输出结构**

```json
{
  "covered": ["Q2", "Q5"],
  "questions": [
    { "id": "Q3", "text": "…", "why": "为什么现在问这个" }
  ],
  "nudge": "我觉得再聊 2 个问题就够出单了"
}
```

`why` 一定要显示出来。用户知道「你为什么问这个」时，回答质量差很多——不是差一点。
`nudge` 是软提示，绝不等于停止。

**出单时的输出**：严格五栏 JSON，每栏是条目数组，不是大段散文（手机上读不动）。

### 3.2 思路确认单

- 五栏，每栏可折叠、可点击编辑（本地改，不回传模型）
- 顶部一行「一句话摘要」：给历史列表用
- 「第 4 栏 第一步动作清单」是强制项，至少 2 条具体动作。
  出不了第一步，说明这份单子还没到能开工的程度——直接提示这一点
- **复制为提示词**的模板：

```
我要做这件事：<intent>
目标与成功标准：<col1>
约束与前提：<col2>
已选定方案（放弃了 X，因为 Y）：<col3>
第一步：<col4>
这些我还没想清楚，别替我决定：<col5>

请基于以上内容直接开始 <任务>，不要重新问我已回答过的部分。
```

### 3.3 场景模板库 + 编辑器

出厂 3 套，问题清单初稿见附录 A（共 27 题，可直接用）。

编辑器需要的能力（不用花哨，能用就行）：
- 改问题措辞、删问题、调顺序、加自己的问题
- 设「必问 / 选问」——必问的 AI 不能跳过
- 自建场景：填名称 + 一句话关注点 + 问题清单
- **场景导入 / 导出（JSON 文件）**：亲友之间互传自己调好的场景模板。
  成本低，但在「小范围分发」这个定位下是最自然的传播方式

### 3.4 历史与跨场景引用

- 历史列表：按场景筛选、按时间倒序、显示摘要行
- 详情页：确认单 + 当时的完整问答（**问答必须一起存**，不然确认单失去可追溯性）
- 「接着深挖」：以旧确认单为上下文开新会话，不清空原单，生成一份新单
- 跨场景引用：新一轮提问开始前，可检索旧确认单并勾选注入
  - 默认注入**摘要**而非全文（省 token、防上下文被历史污染）
  - 最多勾 3 份，超过强制截断
  - 引用关系入库（`citation` 表），详情页能看出「这份结论基于哪几份旧结论」

### 3.5 方案.md 生成器（决策 12）

确认单是给自己看的骨架，方案.md 是**能交给别人看的文档**。输入 = 五栏确认单 +
本次完整问答 + 场景 id；输出 = 一份 Markdown。

尺度取 **E：结构化扩写 + 全段可溯源 + 按场景出不同骨架**。三条硬约束：

1. **扩写不许引入新决策。** 允许口语转书面、加小标题、把并列内容转成表格、
   把你的隐含前提显式写出来；**不允许**新增你没做过的技术选型、数字、日期、人名。
2. **全段可溯源。** 每段带 `sources: [message_id]`。App 内预览时 AI 组织的措辞
   与你的原话用不同样式区分，点一段能跳回当时那条回答。逐条可删。
   落盘的 .md 里以脚注形式保留出处（`[^12]`），拿到文档的人也能验证。
3. **第 5 栏不许被消化。**「还没想清楚的问题」在文档里保留为显式章节
   （标题固定为「待决问题」），不许改写成「后续将持续优化」这类漂亮话。
   这一条是整个功能的安全带——一旦它没了，这份文档的可信度就归零。

**按场景的三套文档骨架**（`plan_skeleton`，存 JSON，编辑器可改）

| 场景 | 文档骨架 |
|------|----------|
| 技术方案 / 架构选型 | 背景与问题 → 目标与非目标 → 约束 → 方案对比表 → 选定方案与设计要点 → 迁移与回滚 → 风险与待决问题 → 排期里程碑 |
| 项目立项 / 需求梳理 | 问题定义 → 目标用户与场景 → 现状替代方案 → 目标与成功指标 → MVP 范围 / 明确不做 → 方案概述 → 资源与排期 → 停损条件 → 待决问题 |
| 复盘 / 总结 | 原定目标 → 实际结果 → 差距归因 → 关键转折点 → 运气 vs 能力 → 下次改什么 → 结论与行动项 → 待验证 |
| 自建场景 | 无骨架时用通用结构：概述 / 结论 / 依据 / 行动项 / 待决问题 |

**落盘**：SAF 一次性授权一个目录（`ACTION_OPEN_DOCUMENT_TREE` + 持久化权限），
之后每份直接写入，文件名 `2026-11-23-缓存改造方案.md`；同时保留系统分享面板。
不要只写 App 私有目录——手机上等于找不到。

**失败与成本控制**：一次调用生成整份文档，中途断了可以从已生成的段落续写；
文档页常驻一个「重新生成」按钮（改了确认单后必须能重跑）。
一份方案约 3~5k token，比提问流便宜，不用担心费用。

### 3.6 调研验证器（决策 13）

**定位：证据不参与塑造你的方案，只检验它是否站在空地上。**

调研放在出单之后，是为了守住一条铁律：**AI 不许因为查到过别人的做法而少问你问题。**
你的答案必须在证据之前完整落地。这是 D 方案比 A/B/C 更本质的地方——
把调研从「启发」降级为「验证」，就避免了笔记里那条最大风险（查到东西就懒得问）。

**边界：调研结果只能写进两处**

| 能进 | 不能进 |
|------|--------|
| 第 2 栏 约束与前提（「已有 X 方案在用，是既成事实」） | 第 1 栏 目标与成功标准 |
| 第 5 栏 还没想清楚的问题（「没人验证过这个规模」） | 第 3 栏 选定方案 |
| 独立验证报告（附录） | 任何「别人都这么做，你也这么做」的建议 |

「别人怎么做」永远不等于「你该怎么做」。第 3 栏一旦被证据污染，
这个产品就从「逼你想清楚」变成了「给你一个看起来对的默认答案」——那就废了。

**四步流水线（一次调研）**

```
1 立题   从确认单抽取 3~6 个可检索问题（AI 起草，你可删改）
         例：「Android Compose + Room FTS5 中文分词的成熟方案」
2 取证   GitHub Search API（见 3.6.2），每个问题取 top 5~8 仓库
3 对照   拿你的方案逐条撞证据，产出四种判定
4 回写   结论进第 2/5 栏 + 生成验证报告附录
```

**第 3 步的四种判定（这是这个功能的全部价值，别退化成「搜到一堆链接」）**

| 判定 | 含义 | 语气 |
|------|------|------|
| ✅ 常见做法 | 你的方案与 ≥3 个独立项目一致 | 「你不是孤例」 |
| ⚠️ 反模式 | 证据里**明确被抱怨/被拒绝**的正是你要做的 | 必须引用原话 issue |
| ❓ 无人区 | 搜遍没找到同类 | 「这块没人验证过，风险自担」——最值钱的结论 |
| 🔍 已知坑 | 同类项目的高频 issue 主题 | 附 issue 链接，可直接读 |

「无人区」是四种判定里最有价值的。多数工具只敢说「找到了什么」，
敢说「什么都没找到，所以你要么是真新，要么是你没搜对」才是验证的意义。
判定时必须写明搜索覆盖了哪些关键词，否则「没找到」不成立。

#### 3.6.1 GitHub 为主源：调用链

以 GitHub 为主，因为它同时提供**代码 + 讨论 + 时间戳 + star**，是唯一的
「有人真做过、还留下了争吵记录」的公开源。

```
优先级 1  repo search      q=<关键词>            &sort=stars&order=desc
优先级 2  issue search     q=<主题> in:title,body type:issue   （挖「已知坑」）
优先级 3  code search      q=<API名> language:kotlin            （验可行性）
补充      README / SKILL.md / docs/*.md 原文（验证「常见做法」不能只看简介）
```

**读原文，不读简介。** 我这次调研的转折点，正是把 grill-me 那 5 行原文和
`native-question-tool.md` 的拒绝理由拉下来读了——简介给人的是「有同类产品」，
原文给人的是「该改哪 12 条」。所以取证这一步必须含一次原文抓取，
只抓 markdown / README，不抓源码全量（手机端流量与内存都撑不住）。

**非 GitHub 补充源**（默认关，设置里可开）：仅当 GitHub 判为「无人区」时，
再走一次通用网页搜索确认「真没人做」还是「GitHub 上没人做」。
这条开关存在的意义就是让「无人区」这个结论敢下。

#### 3.6.2 GitHub 令牌接口（用户点名要预留）

四条来源，按优先级解析；**手机上不存在环境变量和 gh CLI**，
所以我上一轮口述的四条里那两条已按现实替换：

| 来源 | 场景 | 存储 |
|------|------|------|
| 1 App 内填 **PAT** | 主力。`settings > fine-grained token`，只勾 `contents:read` + `issues:read`（公开仓库），最小权限 | **Keystore + EncryptedSharedPreferences**，与模型 Key 同一套，绝不进普通 SP、绝不进日志 |
| 2 **匿名** | 没 token 时用；Search 限流 **10 req/min**、Core **60/hr** | — |
| 3 **代理 / 镜像 base URL** | 直连 GitHub 不稳时的逃生口：可填自建 API 代理或 `ghproxy` 类镜像的 base | 普通设置项，明文（不含凭据） |
| 4 **导出为提示词** | 手机端实在连不上时，把「立题」那 3~6 个问题打包成一段 prompt，用户拿去桌面端跑，结果粘回 App | 走已有导出能力 |

第 4 条是**必须保留的**降级：用户既然已经用别的 AI 干活，
让调研能「离线外包」比硬啃网络超时更划算，成本几乎为零。

**Token 处理三条红线**
- 任何 UI / 日志 / 崩溃报告 / 导出文件里都不出现 token 明文（只显示后 4 位）
- token 只发往**白名单 host**（默认 `api.github.com` + 用户显式填写的代理域）；
  第三方网页搜索结果里的链接一律不带 token
- 设置页有「一键清除 token」，且清除时连带清掉内存缓存

#### 3.6.3 针对「直连超时」的工程处理

用户已明确说直连会超时，这**不是异常，是本产品的默认运行条件**（中国大陆网络 +
手机网络切换 + GitHub API 抖动三重叠加）。设计目标不是「不失败」，而是
**「失败了也让用户拿到有用的东西」**：

1. **单请求预算**：`connect-timeout 12s`、`read-timeout 25s`、`call-timeout 30s`，
   整体一轮调研硬上限 **60s**。超了就出结果，不出进度条。
2. **重试纪律**：只对**连接层**失败（超时/拒连/DNS）退避重试 2 次（0.5s、1.5s）；
   对 4xx/5xx 一律不重试；**已成功的请求绝不重放**（token 配额有限）。
3. **部分成功是正常态**：并行发起 N 个检索，回一个算一个，
   60s 到就用手里的结果。报告顶部如实标注「证据覆盖 3/6 问题，2 个源超时」——
   **绝不假装完整**。调研的可信度取决于它敢不敢说自己没查全。
4. **失败可见**：某个源挂了就在报告里留一行「❌ 未能取得 X 的证据（网络）」，
   而不是静默少一类结论。静默失败的「无人区」是有害的。
5. **结果缓存**：按查询关键词缓存 24h（同一份确认单重跑调研不该再打网络）。
6. **网络状态预判**：起调前读一次 `ConnectivityManager`，无网络直接走降级第 4 条，
   不浪费用户 60 秒。
7. **代理可失败回退**：填了代理 base URL 时，代理失败自动回退直连（一次），
   反之亦然——因为网络状况本身在变。

**一轮调研的开销**：约 6~14 次 API 调用 + 原文抓取，token 消耗集中在第 3 步对照
（约 4~8k）。频率上它是「偶尔做一次的重活」，不是每份确认单必走，
所以放成方案页/确认单页的一个显式按钮，不进主流程自动执行。

## 四、数据模型

Room（SQLite），本地优先，无服务端。

```
scene(  id, name, focus, builtin, created_at )
question( id, scene_id, order, text, why, required )
session(  id, scene_id, intent, status[open|done|draft],
          created_at, updated_at )
message(  id, session_id, role[user|ai], text, questions_json,
          covered_json, created_at )
sheet(    id, session_id, summary, col1..col5, edited_json,
          created_at )
citation( session_id, sheet_id, order )
plan(     id, sheet_id, scene_id, skeleton, markdown,
          sources_json, file_uri, created_at, updated_at )
research( id, sheet_id, plan_id, questions_json, status[queued|partial|done|failed],
          coverage, elapsed_ms, created_at )
evidence( id, research_id, question_idx, kind[repo|issue|code|web],
          repo_full_name, html_url, title, snippet, stars, pushed_at, raw_path )
verdict(  id, evidence_id, judgement[common|antipattern|unexplored|known_pit],
          rationale, quoted_text, quoted_url, applied_to[col2|col5|appendix] )
```

`session.status = draft` 撑起「未完成思路」的恢复。
`edited_json` 存用户对确认单的手工修改，保证重新导出时不丢编辑。
`plan.sources_json` 是段落级溯源（`[{para, message_ids}]`），一份确认单可对应多份
plan（改了单再重生成），按 `updated_at` 取最新。
`research.coverage` 记「N/M 问题取得证据」，配合 `status=partial` 使用——
**部分成功是本功能的正常态，不是错误态**。
`evidence.raw_path` 指向抓下来的原文（存在 app 私有目录，30 天清理）；
只有原文进过库，`verdict.quoted_text` 才可验证。
`verdict.applied_to` 用数据库约束强制「只能写第 2/5 栏和附录」这条铁律。

## 五、技术架构

```
app/
 ├─ ui/          Compose：5 屏（场景选择 → 提问流 → 确认单 → 方案预览 → 验证报告）+ 2 面板（历史、编辑器）
 ├─ domain/      QuestionEngine、SheetBuilder、PlanBuilder、ResearchVerifier、SceneRepository
 ├─ data/        Room + DAO、DataStore(设置)、FileProvider(导出)、DocStore(SAF 持久授权)
 ├─ research/    GitHubClient（含超时/退避/部分成功）、EvidenceCache、WebSearchClient(可关)
 └─ remote/      LlmProvider 接口 → OpenAiCompatibleProvider
```

- **网络**：OkHttp / Retrofit + SSE 流式。**必须流式**——手机上等 8 秒才跳出一整段文字，
  体感像卡死，会直接毁掉这个产品
- **Key 存储**：Android Keystore + EncryptedSharedPreferences，不进普通 SP
- **Provider**：兼容 `base_url + api_key + model` 三元组填写。
  要支持自定义 base_url（DeepSeek / Kimi / 智谱 / 自建网关都能填）
- **降级**：模型挂了不丢数据——问答已落库，可手动补出单（本地按已有回答拼一份骨架）
- **中文搜索**：M4 第一版直接用 Room 的 `LIKE`。个人数据量是几百条量级，
  全表扫完全够。**不要为了这个上 FTS4/FTS5**——中文分词是另一场仗，而且现在没必要打
- **无账号体系**：数据全本地。这是定位（自用+亲友）给的礼物，别在 V1 把它弄丢

## 七、亲友分发要处理的 7 件事

不上架，但发 APK 给别人，这几条不能省：

1. **稳定的 release keystore**。用 debug 签名的话，你自己更新版本亲友装不上
   （签名不一致）。keystore 备份好，丢了就永远发不了更新
2. **拿到 Key 的引导**——这是亲友最大的门槛，不是你的 App。
   首次启动要有一页图文：去哪注册、在哪充值、在哪创建 API Key、复制哪三个字段
3. **本地崩溃日志 + 一键「把日志发给他」**：不上架就不接崩溃上报平台，
   但亲友遇到闪退时你得能拿到日志。写文件 + 走系统分享，成本极低
4. **隐私说明一页**：数据只存本地、Key 只在本机、请求直连你填的地址。
   别人把真实工作想法交给一个陌生 APK，你至少要把这个说清楚
5. **成本提示**：模型费用走使用者自己的 Key，这一点在设置页写明
6. **GitHub PAT 的引导**（和模型 Key 同级门槛）：去哪建 fine-grained token、
   只勾哪两个最小权限、哪些仓库类型可见。亲友多半没听过 PAT，这页不写清就没人用调研
7. **调研的隐私提示**：检索关键词会明文发给 GitHub（公开 API）。
   如果用户做的是「公司还没公开的项目」，关键词本身可能泄密。
   要在调研前明确告知，并提供「只搜我自己的历史，不外网」的选项

## 八、已知取舍与风险

| 风险 | 说明 | 处理 |
|------|------|------|
| 只有 Android | 选了原生，亲友里的 iPhone 用户装不了 | 接受。若将来 iPhone 用户变多，Web 版做只读确认单是唯一的补丁 |
| 提问质量 = 模型质量 | 弱模型会退化成念题机器，且很难察觉 | M1 时人工对比 2~3 个模型再定推荐；设置页保留「模型质量提示」 |
| 全量第一版 | 已选 D，工期最长，且跨场景引用在没数据积累时空转 | 用里程碑化解：M1 结束就自用，到 M4 时正好有真数据可引 |
| 用户懒得答 | 一次问 4 个问题，手机上打字是负担 | 允许一句语音式流水账，AI 自己拆到各问题上；每题给「跳过」 |
| 确认单没人再看 | 出了单不回流到工作，价值归零 | 「复制为提示词」是第一出口，把它放在保存之前，且成功页直接给 |
| **方案.md 有幻觉** | 「一份看起来完整的文档」和引擎的「不编造」原则天然冲突 | 扩写不许引入新决策 + 段落级溯源 + 「待决问题」章节不许被漂亮话消化。文档不是结论的权威来源，问答才是 |
| **调研污染了决策** | 查到「别人都这么做」后，AI 少问你问题，或直接把它变成你的选定方案——产品退化成「给个看起来对的默认答案」 | 流程顺序锁死（问→出单→生成→调研）+ 数据库层 `applied_to` 只允许第 2/5 栏 + 第 3 栏出现证据引用即报错 |
| **「无人区」误判** | 没搜到 ≠ 没人做。搜错关键词就敢下「你是第一个」，是最有害的结论（给用户虚假信心） | 判定为 unexplored 时必须列出「已覆盖的关键词组合」，且需走一次通用搜索复核；否则只能说「未取证」 |
| 调研超时导致功能被弃用 | 用户明确反馈过直连 GitHub 会超时；连续几次拿不到结果，按钮就被永久忽略 | 60s 硬上限 + 部分成功正常出报告 + 离线外包（导出为提示词）兜底。**宁可残缺也不空手** |

## 附录 A：三套出厂场景的问题清单

### A1 技术方案 / 架构选型

1. 这次要解决什么问题？如果**不上这个方案**，现在最痛的具体表现是什么？
2. 边界条件：时间、人力、预算、必须复用的现有系统、绝对不许引入的东西
3. 候选方案有哪些？把「什么都不做」也算一个候选
4. 各方案在三个维度上的差异：一次性建设成本 / 长期维护成本 / 出错后的可逆性
5. 真实规模：现在多少量，一年后**预期**多少量？（防过度设计）
6. 谁长期维护这套东西？他熟悉什么、不熟悉什么
7. 有没有人已经踩过这个坑？内部先例、外部案例
8. 出现什么信号说明选错了？退路是什么，退一次要多久
9. 这次决定要留下什么记录？多久之后回看它

### A2 项目立项 / 需求梳理

1. 问题是谁的？描述一个你**亲眼见到的**具体场景，不要写抽象人群
2. 他们现在怎么凑合解决的？（暴露真实痛度 + 你的真正对手）
3. 不解决会怎样？谁最难受，难受到什么程度
4. 第一版只服务谁？**明确不服务谁**
5. 上线 4 周后看哪个数字？多少算成，多少算没成
6. 最小闭环是哪一段？砍到最后必须留下的那一个动作
7. 明确不做清单（防止范围自己长出来）
8. 有没有不做产品就能验证的办法？最便宜的验证是什么
9. 资源：谁做、多久、钱从哪来、现在最容易卡在哪
10. 停损点：什么情况下你愿意主动关掉它

### A3 复盘 / 总结

1. 当时定的目标是什么？（引原话，不要事后改写）
2. 实际结果是什么？用数字或具体证据描述
3. 差距在哪？是执行问题，还是**目标本身定错了**
4. 关键转折点：哪件事之后，结果其实就定了
5. 重做一次，你会砍掉哪一步、加上哪一步
6. 哪些是运气，哪些是可复制的能力？诚实区分
7. 有没有当时觉得不重要、现在看是关键的事
8. 下次遇到同样局面，第一句该提醒自己什么
9. 这次的结论要写进哪件未来事项的确认单里

三条格式纪律：
1. **坏消息放最前**。一份只说「你的方案很好」的报告没有价值，也养不出使用习惯
2. **「证据覆盖 N/M」必须在顶部**。缺了多少就说什么不成立，绝不静默
3. **无人区必须附「已覆盖关键词」**，否则「没找到」三个字不许出现

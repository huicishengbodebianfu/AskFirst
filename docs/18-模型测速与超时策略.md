# 模型测速与超时策略

日期：2026-11-24 · 网关：magpie（192.168.1.6:3425，107 个模型）· 设备：HONOR TFY-AN00

## 1. 模型测速（host 侧，脚本 `tools/bench_models.py`）

方法：`stream=true`，prompt「用一句话解释浏览器缓存，不要超过 60 字」，`max_tokens=96`，`temperature=0.3`；
每个模型跑 2 次取中位数；测首字延迟（首个非空 delta）、总耗时、输出速度。

| 模型 | 首字(中位) | 总耗时(中位) | 正文字数 | 速度 | 结论 |
|---|---|---|---|---|---|
| `auto/glm-5.3` | 2.02s | 2.64s | 56 | 21.2 字/s | ✅ 快且稳（默认推荐） |
| `auto/qmodel_latest` | 1.76s | 2.00s | 36 | 18.0 字/s | ✅ 最快，输出偏短 |
| `auto/gpt-6.1-sol` | 2.55s | 3.25s | 37 | 11.4 字/s | ✅ 可用，偏慢 |
| `auto/kmodel_latest` | 4.76s | 5.40s | 45 | 8.3 字/s | ⚠️ 最慢 |
| `auto/deepseek-v4.1-flash` | — | 1.33s | **0** | 0 | ⚠️ 96 token 内**没有正文**（先输出思考过程） |
| `auto/hy4-flash-free` | — | 2.40s | **0** | 0 | ⚠️ 同上 |
| `auto/claude-sonnet-4-5` | — | — | — | — | ❌ 网关上游连不上（500） |

**两个"0 正文"的模型对 AskFirst 是不能用的**：引擎要求模型直接回 JSON；如果它先把 1200 token 的预算烧在思考上，
用户会等很久且拿不到 JSON。所以模型推荐里把它们排除，并在设置页的测速里把这种情况明确报出来：
「模型没吐出任何正文（可能只输出了思考过程）」，而不是显示"0 字每秒"。

## 2. App 内的「测一下速度」

设置页模型服务下面新增按钮：一次 64 token 的流式请求（提示词「用一句话说明缓存的作用，不要超过 30 字」），
结果写成一句人话：

```
首字 1820ms · 总共 2410ms · 约 18.6 字/秒（45 字）
```

- 30 秒没结果 → 按超时处理（`AppError.Timeout(30000)`），文案「等了 30 秒没回音…」
- 模型只回思考不回正文 → 明确报"没吐出任何正文"，不假装 0 字每秒
- 失败/限流/无网 → 复用统一的 `AppError` 文案

## 3. 超时预算（全套）

| 层 | 预算 | 说明 |
|---|---|---|
| OkHttp 连接 | 15s | 连不上就别耗着（DNS/拒连/切网） |
| OkHttp 读 | 90s | 流式单次读的上限；正常一轮不会到这 |
| 调 `ping`（测试连通） | **20s** | 设置页点一下就能验 Key/地址 |
| 测速 | **30s** | 64 token 的小请求 |
| 引擎单轮（提问） | **75s** | 实测最慢模型 5.4s；75s 是"明显不正常"的线 |
| 引擎重试（坏 JSON 后一次） | **40s** | 与首轮合计最坏 115s，期间 UI 一直在显示进度字数 |
| 出单 | **100s** | 一次要吐 1~2k token，比提问重 |

到达预算后：`AppError.Timeout` → 界面显示「等了 N 秒没回音…」+「重试」；出单失败额外给
「先用手里这些内容出单」（本地降级，第 5 栏如实写空）。**任何一层都不允许无限转圈。**

## 4. 验证

**JVM 单测（已绿，87 个用例中的 6 个与此相关）**——把预算注入成 100ms，用"永不返回"的假 provider 验证：

| 用例 | 断言 |
|---|---|
| `QuestionEngineTest.模型卡住时按单轮预算超时 而不是无限等` | 收到 `Failed(Timeout)`，且没有 `Decided` |
| `SheetBuildTest.出单卡住时按预算超时 并标记可降级` | `Failed(Timeout, canFallback=true)` |
| `SpeedTesterTest.模型卡住时按 30 秒预算超时` | `Err(Timeout)` |
| `SpeedTesterTest.模型只吐空内容时明确报错` | `Err(BadJson)`，文案含"没吐出任何正文" |
| `SpeedTesterTest.provider 失败时透传可读错误` | `Err(RateLimited)` |
| `SpeedTesterTest.正常回答能给出首字与字数` | `Ok`，`readable()` 含"字/秒" |

> 说明：`runTest` 的虚拟时间只能证明"预算逻辑生效"，不代表真机 75s 与 OkHttp 取消的真实交互。

**假服务端两个口**（`tools/fake_sse_server.py`）：`8084` 发完 SSE 头就挂住、`8085` 40s 不回。

**真机验证（2026-11-24 14:06~14:09，debug 包）**：

| 用例 | 命令 | 结果 |
|---|---|---|
| ping 20s | `--es base_url http://127.0.0.1:8085/v1 --ez demo_ping` | `ping in 20026ms -> Err(AppError$Timeout: 等了 20 秒没回音…)` ✅ |
| 引擎单轮 75s | `--es base_url http://127.0.0.1:8084/v1 --ez demo_run` | 14:07:39.361 起 → 14:08:54.535 止（**75.17s**），`LlmStream: 流结束：0 字 … failure=等了 75 秒没回音`，且没有产生决策 ✅ |
| App 内测速（真网关） | `--es base_url http://127.0.0.1:3425/v1 --ez demo_speed` | `Ok(SpeedResult(firstTokenMs=1421, totalMs=2000, chars=29))` ✅ |

**这一步踩到一个关键实现错误（已修）**：一开始用 `withTimeout` + `Job.invokeOnCompletion { call.cancel() }` 想"协程超时就取消请求"，
真机上根本不触发——协程的阻塞读卡在 socket 上，`invokeOnCompletion` 要等协程体自己结束才回调，等于没有超时。
最终方案：**把所有预算交给 OkHttp 的 socket 级超时**（`callTimeout` / `readTimeout`，每个请求按需克隆客户端），
协程层的 `withTimeout` 只作为假 provider（单测）的协作式兜底。

**另一个坑**：第一版用"`if (…) client.newBuilder()… else client` 的表达式 + 协程取消钩子"触发了 Kotlin 2.2.20 的
IR lowering 崩溃（`Parent of this declaration is not a class: … [companion]`，kaptGenerateStubs 阶段，clean 也复现）。
把那段重写成"私有函数 `clientFor(timeoutMs)` + 无协程钩子"后编译正常。结论：**这类编译器内部错误先去最小化触发代码，
不要重装 Gradle/清缓存**（clean 复现过，清缓存无效）。

## 5. 对产品的影响

- 模型选择：默认 `auto/glm-5.3`（首字 ~2s、21 字/s、JSON 合规）；备选 `auto/qmodel_latest`。
  **别用** `deepseek-v4.1-flash` / `hy4-flash-free`（只思考不回正文，引擎会等到超时）。
- 首次配 Key 的朋友：先点「测试连通」（20s 内必有结果），再点「测一下速度」；两个都过了再开始用。

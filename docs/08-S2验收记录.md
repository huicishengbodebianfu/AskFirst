## 4. 这一步踩到的新坑

### 4.1 增量编译产生"幽灵未解析引用"（最坑）

现象：改一个文件后 `:app:compileDebugKotlin` 报
`Unresolved reference 'AskFirstTheme' / 'AppJson' / 'ScaffoldScreen'`——**这些符号明明存在**，
而且只报"被别的包引用"的那几行；`clean` 后立刻恢复正常。第一轮还赶上 Gradle 守护进程 OOM 崩溃（见 `07-S1`），
崩溃留下的 Kotlin 增量缓存进一步恶化。

处置（已写进 `gradle.properties`）：
```
kotlin.incremental=false
kapt.incremental.apt=false
```
代价是每次编译变全量（本项目 1.5~3 分钟，可接受）；收益是**不再需要靠 clean 排障**。
如果以后工程变大想开回增量，必须先复现并定位（不是简单删掉这两行）。

### 4.2 仪器测试 `Starting 0 tests / Process crashed`

现象：`connectedDebugAndroidTest` 连 0 个用例都没跑就崩；crash buffer 里是之前 `uiautomator dump`
留下的 `UiAutomationService already registered`（HONOR 上 uiautomator 曾被系统 kill）。
处置：`adb reboot` 后同一命令 **4/4 通过**。结论：**uiautomator 在 HONOR 上会污染 UiAutomation 注册，
跑过它之后必须重启设备再跑仪器测试**。

### 4.3 PowerShell 的 `$pid` 是只读自动变量

`$pid=(adb shell pidof …)` 直接报"无法覆盖变量 PID"。改用 `$appPid`。

## 5. 与施工清单的偏差

1. S2 里"测试连通"按实现顺序需要 Provider 的最小能力，所以 `LlmProvider` 在 S2 就有了
   `config()` + `ping()` 两个方法；`stream()` 留给 S3（接口只加方法，不改已有签名）。
2. 为了让设置页能被截图验证，`MainActivity` 加了 3 个 debug-only intent extra
   （`open_settings` / `seed_dummy_key` / `clear_key`），release 构建无副作用。S5 接入
   navigation-compose 后 `open_settings` 仍可用（深链调试的雏形）。
3. 设置页暂时由 `MainActivity` 的本地布尔状态切换（S5 换 NavHost），避免现在为了一个页面引入导航栈。

- 「测试连通」的成功路径还没在真机跑过（需要真 Key）。失败路径已由仪器测试覆盖。
